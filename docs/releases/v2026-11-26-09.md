**Downloads**
- `mp3redactor-setup.exe`: installs the program for you alone (no administrator rights), with a Start menu entry.
- `mp3redactor.exe`: one file, runs from anywhere.
- `mp3redactor-linux-x86_64.tar.gz`: the Linux build (added a few minutes after the release appears).

**A copy of an earlier version must be updated by hand this once**: download one of the files above. From this
release on, Help > Check for Updates installs new versions itself.

**In short**
- **Fewer tools to install.** The integrity check and fix (mp3val) and key detection (keyfinder-cli) are now built
  in, checked against the real tools: same findings and byte-identical fixed files on 1,253 test files, same key on
  every test file. mp3val.exe and keyfinder-cli are only fallbacks now; ffmpeg/ffprobe and fpcalc are still
  external tools.
- **Any file name works.** Files whose path has letters outside the Windows code page (Polish, Czech, Cyrillic,
  Greek, Japanese, ...) are now checked, fixed and get a key. Such files never got a Key tag before: run Detect Key
  on them once to fill it in.
- **Redact fixes integrity problems again** ("Fix problems" is on by default; a saved recipe is switched on once),
  and a fixed file is stamped with what it is after the fix.
- **Check for Updates installs new versions itself**, and there is a Windows installer.

Everything since v2026-11-26-01 (8 versions):

## 2026-11-26#09 -- Redact fixes integrity problems again by default -- redactor_common 2026-11-26-02

- **Redact repairs what the integrity check finds.** The Integrity step's "Fix problems" option is on by default
  again: fixable problems are repaired on Redact's working copy, the file is checked again and that result is
  stamped. It had been off by default since 2026-10-13#04 (review point A14), so Redact only reported warnings and a
  separate Fix Integrity Issues pass was needed afterwards.
- **Saved recipes are switched on once.** A recipe saved while the option was off by default has it stored as off.
  The first time the settings are loaded after this update it is turned on, once; if you turn it off again in Edit >
  Edit Redact Recipe, that stays. A recipe file given with `--recipe` on the command line is used as it is.

## 2026-11-26#08 -- Check Integrity checks four files at once -- redactor_common 2026-11-26-02

- **Check Integrity is faster on a network share.** It now checks four files at once, as Detect BPM and Detect Key
  already do. Measured on a 130 MB album on the home server: 17.2 s down to 12.6 s when the files were not cached,
  5.0 s down to 2.9 s when they were. On a local disk it makes no difference (the check is quick Python work that
  runs one file at a time either way). Cancel stops files that have not started; the ones running finish.
- Fix Integrity Issues still fixes one file at a time, on purpose: it rewrites files and keeps backups.

## 2026-11-26#07 -- Fix Integrity Issues stamps what the file is after the fix -- redactor_common 2026-11-26-02

- **A fixed file is no longer stamped with the problems it had before the fix.** mp3val -f, and the built-in port of
  it, report what they found before rebuilding the file. Fix Integrity Issues stamped that, so a repaired file still
  showed WARNING (for example "MPEG stream error") until it was checked again. It now checks each fixed file once more
  and stamps that result: OK when everything was repaired, or what is left that a fix cannot change (too few MPEG
  frames, no tags, ...). If that second check fails, the file shows TOOL ERROR and is not stamped. The Redact step
  already checked again after a fix and is unchanged.

## 2026-11-26#06 -- The integrity check and fix are built in: mp3val.exe is no longer needed -- redactor_common 2026-11-26-02

- **Check Integrity and Fix Integrity Issues work without mp3val.exe.** They now run in-process in
  `core/mp3_validator.py`, a Python port of mp3val 0.1.8 that follows its C++ function by function, quirks included.
- **Same results as before.** On 1,253 test files (real encodes at MPEG 1, 2 and 2.5, Layer II, VBR with and
  without a Xing header, synthetic streams with CRCs, VBRI headers, APEv2 tags and RIFF wrappers, files damaged on
  purpose, and 1,000 randomly mutated files) the port printed the same WARNING/ERROR/INFO lines as mp3val.exe for
  every file, and the fix wrote byte-identical files and the same .bak backups, with and without "delete .bak".
  About ten times faster. `tools/compare_mp3val.py <folder> --exe <mp3val.exe> --fix` repeats the comparison on any
  music folder (the fix only ever works on copies) and writes a report.
- **Files with any letters in their path are checked.** mp3val.exe could not open a path with letters outside the
  Windows code page (Polish, Czech, Cyrillic, Greek, Japanese, ...): since 2026-11-26#05 those were TOOL ERROR, now
  they are checked and fixed like any other file.
- A file mp3val.exe would hang or crash on (for example a tag whose size field points backwards) is TOOL ERROR with a
  message saying why, at once instead of after the 30-second timeout.
- mp3val.exe stays as a fallback only if the port itself fails on a file, if it is installed; it is optional now.
- Not changed: as with mp3val -f, the result of a fix lists the problems found before the rebuild, not what remains.

## 2026-11-26#05 -- mp3val no longer passes files it could not open as clean -- redactor_common 2026-11-26-02

- **Integrity check: a file mp3val cannot open is no longer reported as clean.** mp3val 0.1.8 cannot open a path with
  letters outside the Windows code page (Polish, Czech, Cyrillic, Greek, Japanese, ...; Norwegian letters and ü are
  fine). It then prints "Cannot open input file" on stderr and exits 0 with no WARNING/ERROR line, so the file was
  stamped OK without being read. It is now TOOL ERROR (never stamped), and the message says to rename the file or
  folder. The same goes for Fix, which never touched such files.
- fpcalc 1.6.2 (Look Up by sound) was tested the same way and opens every name.

## 2026-11-26#04 -- Key detection is built in: keyfinder-cli is no longer needed -- redactor_common 2026-11-26-02

- **Detect Key works without keyfinder-cli.exe and its four FFmpeg DLLs.** The key is now found in-process by
  `core/key_detector.py`, a Python/NumPy port of libkeyfinder 2.2.8 (the engine inside keyfinder-cli), with its
  constants and steps copied from the C++. aubio decodes the audio (as for BPM); ffmpeg decodes when aubio cannot.
- **Same keys as before.** On 40 test files (real tracks and synthetic tracks in all 24 keys, MP3 and WAV, 44.1 and
  48 kHz) the port gave the same key as keyfinder-cli 1.2.0 on every one, with both decoders, at about 0.3 s per file
  against 0.8 s. `tools/compare_keyfinder.py <folder>` repeats the comparison on any music folder and writes a report.
- **Files with non-English letters in their path now get a key.** The Windows build of keyfinder-cli could not open
  any file whose path held a letter outside plain ASCII (å, ø, æ, ü, Polish, Japanese, ...): Detect Key failed on them
  with "Unable to open audio file". The built-in detector reads them (tested in tests/test_key_detector.py).
- keyfinder-cli stays as a fallback for a file the port cannot decode, if it is installed; it is optional now.
- numpy is listed in requirements.txt (it was only there through aubio before).

## 2026-11-26#03 -- Delete Files (Recycle Bin), and the Delete key asks what you mean -- redactor_common 2026-11-26-02

- **File > Delete Files (Recycle Bin)… (Shift+Delete)** sends the selected files to the Recycle Bin, after a Yes/No
  question that lists them. The files leave the list and the status bar says how many went. A file with unsaved
  changes is refused and stays (the warning names it), because trashing it would throw the edits away. If the Play
  window has the file open, it is closed first. It is also in the table's right-click menu.
- **The Delete key now asks.** Before, it only took the files off the list and left them on disk, which is not what
  most people expect from Delete. It now asks Remove from List (the default button, files stay on disk), Delete Files
  (Recycle Bin) or Cancel. Choosing Delete Files does not ask a second time. With nothing selected the status bar
  says to select tracks first. File > Remove from List has no shortcut any more; the two File menu items act at once.
- redactor_common stays on 2026-11-26-02 (the pin moved from 2026-11-26-01 in the update-framework entry below; its Delete-key question is used here for the first time).

## 2026-11-26#02 -- Check for Updates installs the new version itself; a Windows installer -- redactor_common 2026-11-26-02

- **Help > Check for Updates installs the update** instead of only opening the download page. The app is on the
  Redactor family's update framework (redactor_common docs/update-framework.md): every release carries an
  `update-manifest.json` naming each download with its size and checksum, and every copy says how it was put on the
  PC. The portable `mp3redactor.exe` replaces itself (the old one is kept as `mp3redactor.exe.old` until the next
  start) and starts again; an installed copy runs the new installer silently and starts again. When it cannot update,
  it says why, with a Copy details button, and still offers the download page.
- **A Windows installer**, `mp3redactor-setup.exe`: per user, no administrator rights, into
  `%LOCALAPPDATA%\Programs\The MP3 Redactor`, with a Start menu entry. The one-file `mp3redactor.exe` stays the
  portable download. Neither bundles mp3val or keyfinder-cli (put them in `tools\` beside the exe, or on PATH).
- **A copy on an older version must be updated by hand once**: download this release from the release page. Its
  Check for Updates cannot read the new releases' manifest (decided for the whole family: no bridge for old copies).
- The command line has `mp3redactor --check-update [--release-tag vX]` (prints what this copy would do, as JSON;
  changes nothing) and `--update` (does it without a window), for the release gate. `mp3redactor notes PATH --update`
  is still the notes command's own option.
- Releases are now made with redactor_common's release tool (`pyproject.toml`), which builds the exe, the installer
  and the manifest, publishes a pre-release, checks the update from the previous release, and only then makes it
  Latest. The GitHub workflow no longer builds the Windows exe (its upload would replace the file the manifest
  pins); it adds only the Linux download, when the release is published. The Linux build cannot replace itself: it
  says so and opens the release page.
- Shared code moved from redactor_common 2026-11-26-01 to 2026-11-26-02 (the Delete key's new question applies only
  to apps with Delete Files; here Delete still removes from the list).
